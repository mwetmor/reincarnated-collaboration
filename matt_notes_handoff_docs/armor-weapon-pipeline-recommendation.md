# Asset Differentiation Pipeline — Recommendation for the Claude Team

**Purpose:** Define how we turn the JSON content packets into 400 visually distinct classes per season, using the Synty catalogue as the geometry base, the 100k-weapon corpus as a reference library, and a Claude API call to generate armor style parameters.

**Core principle:** We are not mass-generating 3D meshes. Geometry comes from Synty (armor) and from the weapon corpus (weapons). Differentiation comes from a **parametric restyle layer** plus **accent attachments**, driven by structured data. AI generation is reserved for hero legendaries/sets only.

---

## 1. The weapon/armor asymmetry (read this first)

We have opposite situations for the two asset types, and they need opposite treatments.

**Weapons — reference-rich.** ~100,000 weapons already downloaded with geometry, mechanics, and reference images. This is a *catalogue to select and adapt from*, not a generation queue. We only ever surface a few hundred per season.

**Armor — reference-poor, and that's fine.** We are *not* reproducing real armor geometry — silhouette comes from Synty's fixed meshes. So collecting armor reference pictures would mostly go unused. Instead we generate the **style parameters** directly via a Claude API call. Claude *is* the interpretation layer, writing straight into the schema Godot consumes.

---

## 2. Weapon path

Split by tier:

- **Common / magical weapons:** Pick a Synty base weapon mesh, then apply the parametric restyle layer (Section 4). The corpus reference image + metadata tells the restyle system what palette, finish, and motif the weapon should read as.
- **Legendary / Set weapons:** Where existing geometry is unusable or a unique silhouette is warranted, use **image-to-3D** (Rodin via fal.ai, or Tripo) seeded from the actual reference picture. Image-to-3D is far more faithful than text-to-3D — we already have the answer image, so use it.

Rationale: we can't ship 100k meshes meaningfully, and we already own geometry + pictures. Selection + adaptation beats mass generation.

---

## 3. Armor path

Silhouette = Synty mesh (fixed). Differentiation = StyleProfile parameters generated by a Claude API call.

The call takes the class definition **and the matched weapon's theme** (so armor and weapon read as a coherent set) and returns a constrained JSON `StyleProfile` plus flavor text. No downstream interpretation layer needed.

### Differentiation budget per class (apply in this order)

1. **Base mesh choice** — with the full catalogue we have dozens of chest/legs/boot options. Assign *different base meshes* across classes FIRST. This is the cheapest silhouette variety we have.
2. **Accent attachments** — belts, straps, pouches, shoulder pieces, capes via `BoneAttachment3D`. The one lever that changes silhouette on torso/legs. Use these to break "everything's the same shape."
3. **Parametric restyle** (Section 4) — color/finish/overlay. The multiplier on top, not the sole source.

> **Expectation setting:** Two classes sharing the same Synty chest mesh are the same *shape*. Color/finish/overlay disguises this well at gameplay distance in Synty's stylized idiom, but won't fool side-by-side study. That's why base-mesh spread + accents come first; restyle is the multiplier.

---

## 4. The parametric restyle layer (one shader, 400 profiles)

Synty assets are flat-shaded, low-poly, palette-textured — essentially uncolored geometry painted by a palette. That makes them ideal for shader-driven reskinning. **Build ONE master `ShaderMaterial`** (or a small set keyed by armor type) that reads a profile resource. Do **not** author 400 shaders — keeps material count and draw calls under control.

Stacked dimensions, all driven from the StyleProfile:

1. **Palette remapping (biggest lever)** — map UV regions to a 4–6 color `class_palette` (primary, secondary, trim, metal, accent, leather). Hundreds of distinguishable looks from this alone.
2. **Material/finish per region** — metalness/roughness/specular per UV zone. Same chestplate → matte cloth / burnished bronze / lacquered black / worn iron.
3. **Emission / glow masks** — emissive trim, runes, edge-glow driven by rarity. Reads cleanly on Synty's flat surfaces; use for magical + legendary tiers.
4. **Detail/pattern overlays** — triplanar or UV overlay textures (scales, weave, damask, hex, scratches) blended via mask. ~20 overlays × palette × finish multiplies combinatorics hard.
5. **Procedural wear/edge effects** — edge-detection darkening, crevice dirt, fresnel rim. Cheap tricks that imply different craftsmanship tiers.
6. **Secondary mesh accents** — the silhouette-breaker from Section 3.2.

---

## 5. StyleProfile schema

Per-class resource (Godot `.tres` or JSON) consumed by the master shader. The engine emits this; the Claude API call fills it. Suggested fields:

```
class_id              : string
base_mesh_set         : [synty mesh refs]   # chest, legs, boots — assigned upstream
palette               : [hex; 6]            # concrete values, not names
finish_per_region     : [enum]              # from valid-values manifest
emission_mask         : id | null
emission_color        : hex
emission_intensity    : float
overlay_texture_id    : id                  # from valid-values manifest
overlay_tiling        : float
overlay_mask          : id
wear_amount           : float (0..1)
rim_color             : hex
accent_attachments    : [synty attachment refs]  # real meshes only
flavor_text           : string
theme_seed            : string|int          # shared with matched weapon
```

---

## 6. The Claude API call (armor StyleProfile generation)

Get these right — they are the difference between usable output and silent breakage:

- **Pin the output schema hard.** Return ONLY JSON matching the exact StyleProfile fields. Palette as concrete hex. Finish as enum values the shader knows. Overlay/accents as IDs from our actual libraries.
- **Hand it the valid-values manifest as its menu.** The prompt must include the enumerated list of valid finishes, overlay IDs, and Synty accent meshes. The model may pick ONLY from these. *Biggest failure mode:* a model inventing `"overlay": "ancient_dwarven_filigree"` that no asset resolves to.
- **Feed it the constraint, not just the vibe.** Tell it which base mesh was assigned, so palette/accents are chosen for that silhouette. A bulky-plate profile looks wrong on a light-robe mesh.
- **Link weapon + armor theme.** Pass the matched weapon's palette/motif (`theme_seed`) into the armor call so they harmonize. Otherwise: museum saber + mismatched armor.
- **Batch and cache.** 400 classes/season is bounded and one-time-per-season. Generate profiles in a batch run, store as versioned resources. **No runtime API calls** — we pre-bake a season's style sheet.

---

## 7. End-to-end pipeline

```
Engine emits: class def + matched weapon (from 100k corpus)
        │
        ├─ Weapon: Synty base + restyle params (common)
        │          image-to-3D from reference pic (legendary/set)
        │
        └─ Claude API call → armor StyleProfile
                            (constrained JSON, theme-linked to weapon)
        │
        ▼
Both land as Godot resources (.tres / JSON)
        │
        ▼
Master shader + BoneAttachment3D accent system
        │
        ▼
400 distinct class looks   (legendaries/sets peel off to image-to-3D)
```

---

## 8. Prerequisite before generating anything

**Author the valid-values manifest first.** The enumerated list of: available finishes, overlay texture IDs, and Synty accent meshes. This single artifact is:

- the **menu** handed to the Claude API call (so it can only choose things that exist), and
- the **vocabulary** the master shader reads from.

Get this authored once and the generation step and the rendering step speak the same language. Everything downstream depends on it.

---

## 9. First proof to build

Take 3–4 classes. For each: assign a Synty base set, generate the armor StyleProfile via the constrained call, render through the master shader, attach accents via `BoneAttachment3D`, and match one weapon from the corpus (one common via restyle, one legendary via image-to-3D). Drop into the existing 6-area battle sim. This validates: (a) does the constrained call produce schema-valid output, (b) does the restyle read as distinct, (c) real cost-per-asset for the image-to-3D legendaries — the numbers that decide whether 400/season is sustainable.

---

## Tooling reference (legendaries/sets only)

- **Rodin (via fal.ai)** — best for an automated pipeline; native quad topology, 4K PBR, text or image input. Heaviest/priciest meshes but fine for a bounded hero set.
- **Tripo API** — cheapest credits, fast, decent topology; good for higher volume.
- **Meshy API** — strongest texturing, best-documented API; good for props.

Image-to-3D (seeded from corpus reference pictures) is the preferred mode — far more faithful than text-to-3D.

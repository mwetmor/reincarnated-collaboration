## §1 — COMMIT 1: M-9 (no-`else` strict-raise) + M-7 leg (b) (`A-FRZ-1` executable)

### 1.1 What the defect was, and what this landing is NOT

`resolve_skill`'s effect loop branched on exactly 26 names — 10 hand-written literals plus the 16
registry `AILMENT_NAMES` — and carried **no `else`**. An effect whose name was in neither set was
silently skipped and the loop returned `total_damage` unchanged. That is what `{"name": "dot"}` did
in all three banked G-5 batteries: a rider dealing zero damage, every assert passing, nothing in
any artifact saying so.

**This is not a repair.** Exposure today is zero on the broadest base anyone has walked
(jack-ryan's Gate-2 census: 5,110 JSON / 19,642 effect instances, 0 unhandled). M-9 makes the
**next** occurrence loud instead of silent.

### 1.2 The frozenset trap, and why the AST guard is the answer (R-M9-1)

The spec names the trap and I did not fall in it. `_HANDLED_EFFECT_NAMES` has two halves that are
**not** the same kind of object:

- the **ailment half is genuinely derived** — registry-loaded at import, so adding an ailment to
  `config/ailments.yaml` grows it with zero code change (T-M9-3);
- the **literal half is hand-typed**, and a hand-typed mirror of an `elif` ladder drifts from it.
  Someone adds `elif name == "reflect":`, forgets the frozenset, and the guard now reports a
  handled name as unhandled — **the original defect, one layer up.**

So the literal half is pinned by an **AST guard test**, not by discipline: the test parses
`resolve_skill`, walks the `if/elif` chain structurally, collects every string literal compared
against `name`, and asserts set equality with `_HANDLED_EFFECT_LITERALS`. `name in AILMENT_NAMES`
contributes nothing to the extraction (it is a `Name`, not a literal) — the derivation is
structural, not conventional.

**The rejected alternative, and why:** restructuring the ladder into a dispatch dict. That is a
real refactor of the kernel's hottest loop, with real byte-identity risk, to fix a bookkeeping
problem a 30-line test solves. **This landing is AST-guard pinning, NOT a kernel refactor.**

The guard carries its own falsifier (`T-M9-2b`): the extractor is run against a *synthetic* source
carrying an extra `elif name == "reflect":` and must detect the drift. It is synthetic on purpose —
a test that mutates the real module to prove a test works is a test that can leave the module
mutated.

### 1.3 Three states, and why the default is WARN

| state | behaviour | default? |
|---|---|---|
| SILENT | the pre-landing behaviour | **never again — the state is not offered.** `set_effect_name_policy` raises at SET time on anything outside {warn, strict} |
| WARN | log once per distinct name per process; continue | **DEFAULT** |
| STRICT | raise `UnknownEffectName(name, skill_id, sorted(handled))` | explicitly armed |

**Log-once is not a nicety.** At the pre-M-4 claws cadence (10 presses/s) a per-hit log would emit
~150,000 lines per battery, and a guard that floods is a guard that gets disabled — which is the
silent fall-through with extra steps. T-M9-6 measures it: 1,000 unhandled effects across 2 distinct
names ⇒ exactly 2 warnings.

**Promotion criterion, pre-registered so it is not argued later:** STRICT becomes the *global*
default once one full **production** battery (season-generation path, not the replica path) runs
green under it. Not before, not by assertion. It is written into the module docstring so the next
reader finds it at the constant rather than in a note.

**Discipline #12 read, in both directions:** WARN adds log output only. STRICT converts a silent
no-op into an exception — and in the passing case (zero unhandled names, universal today) **no
number moves either.** M-9 is byte-identical in both modes, and §1.6 measures that rather than
asserting it.

### 1.4 M-7 leg (b): the comment becomes an executable (R-M7-2)

Until this landing the protection was **prose**. `kitcal_g5_scenarios.py:472-475` said "no effect
here is `freeze`, and none may become one" — exactly right, and unable to fail a test.

What it guards is Gate-2 H-1's canonical case. GD's own freeze carries **no shatter operator**
(`dmgspecial_freeze_handler.dbr` is a sound cue; EXT-A §1.5 / EXT-B §1.5 cross-validated). RDR's
registry `freeze` is a **different mechanism with the same name**: at expiry, below 25 % HP, it
applies 20 % of max HP as a burst — 149.4 HP on the fixture's 747 pool, i.e. **precisely the
death-2 band, on the gate that grades death-2**, and invisible in every report field because
shatter buckets as DoT damage (`effect_resolver.py:253`).

KC1 §14.22 *repaired* the shatter operator. It now works and still fires zero times because nothing
in generation emits `freeze`. That is **corpus-dormant, not structurally dormant** — a loaded weapon
with the safety documented rather than engaged. `A-FRZ-1` now engages it, and the predicate is
**two-part**: no effect name/element/label is `freeze`, **and** no effect carries
`shatter_threshold_fraction` / `shatter_damage_percent` under *any* name — because a renamed ailment
carrying the shatter parameters is the same burst by another spelling, and a name-only guard passes
it (T-M7-4b).

`--arm-freeze-shatter` makes it **a gate, not a wall**: a future deliberate shatter experiment does
not require editing the guard, and a guard edited to run an experiment is a guard that stays edited.
When armed, the run says so on stdout, in the report body (`freeze_shatter_armed`), in the
assertion list, **and in the artifact filename** (`_frzarmed`) — the §8.1 filename lesson, third
application.

**H-M7-b honoured:** the guard refuses **emission**, never the operator. "Emit freeze but suppress
shatter" would be a content decision wearing a guard's name, and leg (c) — *should RDR generation
emit `freeze` at all?* — is **Matt's** (HALT-1, filed at
`canonical/matt_decision_needed/2026-07-29-rdr-freeze-emission.md`). Nothing in this landing touches
`config/ailments.yaml`; the inherited 0.25 / 0.20 defaults stand unchanged and **unvalidated**
(A-M7-1), which is the honest state — no balance pass has ever run on them because the operator has
never fired.

### 1.5 A-EFF-1, and the ordering that is the whole point of it

`A-EFF-1` arms `EFFECT_NAME_POLICY = strict` in the harness preflight and asserts it is armed.
Arming and asserting are the **same event** on purpose: two separate steps can drift apart.

**Ordering (the WARN-1 lesson, charter §8.1).** `main()` now calls `assert_static_pins(...)`
**explicitly before `drive()`**. `drive` still runs the pins itself, so a programmatic caller is
covered — but the ordering requirement is a *call-site* property and this makes it one, rather than
an incidental consequence of `drive`'s internals. Nothing is written between argument parsing and
that call, so a refusal writes **zero files and creates zero directories**. T-M9-8 measures exactly
that: it poisons every scenario with a `freeze` emitter, calls `main()`, and asserts both the raise
and `not out_dir.exists()`.

**Run-manifest field (P-1's producer).** The report gains `effect_name_policy`, **read from the
kernel at report time** rather than transcribed — a manifest that claims STRICT while the module
sits at WARN is worse than no manifest. P-1 (ratified, charter §8.13) requires the baton emission to
record `strict`; this is the field it will record.

## §2 — COMMIT 2: M-6 (crit labelling) + the two Gate-2 WARN repairs

### 2.1 The four-link chain, and why link 3 was free

Crits already happen: `_apply_crit` fires, rolls and multiplies (`damage_resolver.py:1394-1399`),
and appends `"on_crit"` to the events list. What did not happen is anyone *hearing about it* on the
player's own attacks. Four links, one break:

| # | link | pre-landing state |
|---|---|---|
| 1 | kernel emits the event | **works** — `events.append("on_crit")` |
| 2 | adapter can return events | **works, opt-in** — `return_events: bool = False` |
| 3 | the caller asks for them | **BROKEN on offense.** The only opt-in call site was the mob→player path, further gated on `WIRE_WAVEC_BT or WIRE_WAVEC_MARKS`. The player→mob path left the default |
| 4 | the trace carries it | **absent** — `on_hit` had 17 keys, none of them crit |

Link 3 is free, and the argument is `spatial_resolver_adapter.py:459-465`: `resolve_skill` is
called **unconditionally and identically**, and only then does the function branch on the flag. The
events list is constructed on every call today and **discarded**. Requesting it is a *return-shape*
change, not a behavioural one — no RNG consumed, no branch before the roll.

That is why it lands **UNGATED** (no new flag), and why **byte-identity IS the acceptance test**
rather than a nicety: if the digest moves, R-M6-1's reading of the adapter is wrong, and that is a
finding to halt on, not a delta to explain.

### 2.2 What landed

1. **Offense site** (`_apply_skill_damage`, the resolver-backed branch): `return_events=True`;
   `"on_crit"` per resolved hit captured into a per-hit bool.
2. **Received site** (mob→player): the events request is now **unconditional** rather than gated on
   the Wave-C wire flags. The Wave-C *consumers* stay flag-gated exactly as before — only the
   *request* moved. So "did the boss crit the killing blow" is answerable regardless of Wave-C, and
   given G-B grades a **death**, that question is not idle.
3. **`_frame_on_hit` closure + `ReplicaFrameSink.on_hit`** gain `crit: bool` and
   `crit_multiplier: float | None`, additive and defaulted, serialized through the existing
   `_finite_opt` guard.
4. **One vocabulary bridge, at the logging boundary only.** The kernel emits `"on_crit"`
   (underscore); the Wave-C sim vocabulary is `"on-crit"` (hyphen). The bridge lives where events
   enter `_wave_c_tick_events`. **The kernel literal is NOT renamed** — `damage_resolver` is shared
   with the 1D engine and every non-spatial caller, so renaming it is a cross-seam semantic shift
   for a cosmetic gain (H-M6-b).
5. **Battery report** gains per-tier `crit_count`, `crit_rate`, `crit_share_of_damage`, so the
   N-4 / N-5 crit decomposition is a read rather than a re-run.

**Scope kept (H-M6-d):** M-6 **labels** crits; it does not **consume** them. The moment a crit event
drives a heal this stops being class (B) and stops being byte-identical — that is M-8b, and it
waits for the battery.

### 2.4 Gate-2 WARN #2 — `latency_floor_ok()` is advisory BY DESIGN

`PilotedCompetence.latency_floor_ok()` had no caller but its test. Two dispositions were available:
raise from `__post_init__`, or declare the floor advisory. **The conductor routed the second**
(charter §8.14: *"R-M3-3's floor is advisory, declared as such (Discipline #8)"*), and I built to
the routing rather than to the finding's suggested action.

What that means concretely, because "advisory" must not mean "unwired": the predicate now has a
**caller** — the engine evaluates it when `piloted_competence` is armed and emits a loud one-time
notice when the configured latency is under one tick — and the docstring states that it is
**advisory by design**, with the reason. The reason is that R-M3-3's bracket is **non-corpus**
(0.2–0.4 s action-game convention) and `0.0` is a *legal, deliberately-reported CEILING arm*. A
hard raise would make the ceiling arm unconstructible, which would delete a declared reporting arm
to guard against a typo. Advisory + a caller + a loud notice keeps both.

## §6 — COMMIT 5: the regression found a defect of mine, and named a real one

### 6.1 My defect: A-EFF-1's arming was PROCESS-GLOBAL

`EFFECT_NAME_POLICY` is a module global. The first version of A-EFF-1 called
`set_effect_name_policy("strict")` unscoped in the harness preflight, so in a single pytest process
**every later test in the session inherited STRICT** — and the production emission driver raised
`UnknownEffectName`. Twelve failures with nothing wrong in the code under test.

**That is H-M9-b — "STRICT armed globally by enthusiasm" — arriving by LEAKAGE rather than by
decision**, which is a sharper version of the hazard than the one the spec named. My own test file
had an autouse fixture restoring the policy; the harness's own suite did not, and no targeted run
crosses the two seams.

**The fix:** `effect_name_policy_scope()`. The pins prove arming works and assert it inside a scope
that restores on exit; `drive` arms for the battery's own duration and restores after. "The replica
path does not run unarmed" and "nothing else is armed by accident" are now both true, and T-M9-9b
pins both entry points **plus** the restore-on-exception path.

NOT a `dot`-class silent defect.** Rocket's E2 math note

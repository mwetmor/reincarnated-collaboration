## §0 — The arm, and where its boundary is

### §0.1 The wire is five tools

`tools/list` over the Pro server returns **175 tools**. The `create_particles` family is exactly five:

| tool | what it reaches |
|---|---|
| `create_particles` | makes a `GPUParticles3D` + a fresh `ParticleProcessMaterial`; sets `amount`, `lifetime`, `one_shot`, `explosiveness`, `randomness`, `emitting` |
| `set_particle_material` | direction, spread, velocity min/max, gravity, scale min/max, colour, emission shape (point/sphere/sphere_surface/box/ring) + its dimensions, angular & orbit velocity, damping, attractor toggle |
| `set_particle_color_gradient` | an arbitrary-length colour ramp on `color_ramp` |
| `apply_particle_preset` | eight named presets (explosion, fire, smoke, sparks, rain, snow, magic, dust) — Matt-verdicted judgeable ×3 at PROVISION-CAL |
| `get_particle_info` | full readback: node timing + every material field + the ramp stops |

### §0.2 The split this cell held to (TCP-50), stated so it is auditable

Every MCP call this cell made is in `tmp/l7race/VPRO/wire/*.jsonl` with a tool name, an **intent
string recorded at call time**, a timestamp and a latency. The self-imposed rule:

- **VFX look and behaviour — the five particle tools ONLY.** No exceptions, none needed.
- **Plumbing — `create_scene` / `open_scene` / `save_scene` / `update_property`.** `update_property`
  is used for **`position` and nothing else**, ever. That restraint is the point: `update_property`
  can set *any* property, including `lifetime`, `local_coords` and `draw_pass_1`, and an arm that
  reaches for it makes itself unfalsifiable — the race would no longer be measuring the particle
  surface. Where the particle surface cannot reach, this note records a **ceiling** instead of
  quietly stepping around it.
- **`execute_editor_script` / `execute_game_script` / `create_script` / `edit_script` /
  `attach_script`: NEVER CALLED.** Grep the ledgers.
- **Hand-side, dispatch-permitted and declared:** the capture rig (`scripts/vpro_race_rig.gd`), the
  stage-supplied `draw_pass_1` assignment, `visibility_aabb` (culling), and parenting the wire's
  output to a runtime caster. All four are named in the rig's own header.

**Why a hand-rolled stdio client rather than agent tools:** Claude Code binds MCP servers at session
start, so a server installed mid-session cannot appear as agent tools. `tmp/l7race/VPRO/pro_wire.mjs`
(lineage: `mcp-lab/bin/pro_mcp_client.mjs`, TCP-L2/L4b) speaks the same JSON-RPC to the same server
binary, which relays over WebSocket to the same addon. Same wire; what changes is who types the call.
It also timestamps at microsecond resolution, which is what the race's TCP-32 clock question needs.

### §0.3 ★ Two load-bearing probes, answered at the wire before any authoring

Both were run as a smoke plan (`plans/00b_smoke.json`, 11/11 OK) because the whole CAST design
depended on them.

**PROBE 1 — can a gradient carry ALPHA?** The schema says `color` is `hex '#RRGGBB'`. The source
(`particle_commands.gd::_parse_color`) says `Color.html`, which accepts eight digits. **It does.**
`#88ddff00` round-tripped as `(0.5333, 0.8667, 1.0, 0.0)`.

That single fact is what makes this arm able to answer brief 1 at all. **The wire has no timeline,
no delay, no sequencer and no way to move a node over time.** What it does have is a shared
`lifetime` with `explosiveness = 1.0`, which makes every system burst together on the same period —
and an alpha ramp, which decides *when inside that period* each system is visible. So:

> **a shared lifetime is the wire's clock, and the alpha ramp is its keyframe track.**

**PROBE 2 — does the preset's deferred ramp land?** `_apply_gradient` assigns `color_ramp` via
`set_deferred`, so a readback in the same batch could race it. It does not: at ~100 ms round-trip the
next call already sees the committed ramp. Recorded because it is a real hazard that happens not to fire.

### §1.1 The design, and the two things it had to work around

The geometry is inherited from arm H so the two arms throw down the same corridor at the same camera
(`AXIS = (0.682, 0, −0.732)`, `SPAN = 6`). `prop_r` was **measured** by the rig after the skeleton
posed — `(−4.7746, 1.5260, 3.5635)` world — and the wire was authored to that number, giving a
**11.961 m** throw.

**Every system: `lifetime = 3.00`, `explosiveness = 1.0`, `one_shot = false`, `randomness = 0`.** One
clock, five systems, beats cut by alpha ramps:

| beat | system | window | how the window is made |
|---|---|---|---|
| FLASH | `Flash` 220 | 0.00–0.42 s | ramp fades to α0 at offset 0.140 |
| TRAVEL | `Bolt` 40 + `Trail` 90 | 0.00–0.66 s | kinematics (below) + ramp |
| IMPACT | `Impact` 110 | 0.585–1.26 s | **ramp held at α0 until offset 0.195** |
| GROUND | `Ring` 70 | 0.64–1.59 s | ramp held at α0 until offset 0.198 |

**Travel without a moving emitter.** Arm H translated a node per frame and let `local_coords = false`
leave a wake. Neither is on this wire. The substitute is kinematic: `v₀ = 39.87 m/s` against
`damping = 66.45` comes to rest at exactly `v₀²/2d = 11.961 m` after `v₀/d = 0.600 s` — the measured
throw, solved rather than tuned.

### §1.2 ★ The finding: a velocity BAND is a comet; a velocity SPREAD is a beam

i1 gave the trail a wide band (8 → 39.87 m/s) on the reasoning that a spread of speeds strings
particles along the path. It does — and it produces the wrong picture, for a reason that is pure
arithmetic. Under a shared damping every particle rests at `v²/2d`, and **the slow end never leaves
the hand**:

| band | packet at t=0.10 | at t=0.35 | at t=0.60 |
|---|---|---|---|
| **8.0 – 39.87** (i1) | 0.47 → 3.65 m (**3.19 m**) | 0.48 → 9.88 m (**9.40 m**) | 0.48 → 11.96 m (**11.48 m**) |
| **33.0 – 39.87** (i2) | 2.97 → 3.65 m (0.69 m) | 7.48 → 9.88 m (2.40 m) | 8.19 → 11.96 m (3.77 m) |

i1 is an **11.48 m beam anchored to the caster that merely fills in**. It was caught by measurement,
not by eye: the added-luma census sat between 0.73 M and 1.04 M for **sixteen consecutive frames**
with no beat structure at all. i2's narrow band moves **both** ends (near end 2.97 → 8.19 m) and
stretches 0.69 → 3.77 m — a comet.

Same tool, same damping, one number changed from 31.9 m/s of range to 6.9. Blob-tracking the result:

```
f8  (0.000 s)  flash+bolt co-located (349, 300)        <- the hand
f9  (0.033 s)  flash (349,300)  bolt (509, 323)
f14 (0.200 s)  flash (349,300)  bolt (720, 348)
f17 (0.300 s)  flash (350,299)  bolt (819, 365)
f23 (0.500 s)  flash gone       bolt (902, 376)
f26 (0.600 s)  IMPACT (938, 364) n=14424 px            <- arrival
```

Monotonic travel across 430 px with the flash pinned at the hand throughout. *General form:* under a
shared damping, **velocity RANGE sets the packet's length and velocity MINIMUM sets whether its tail
ever leaves the origin.** A trail wants a narrow band placed high, not a wide one placed low.

### §1.3 ★ The ceiling that shaped the whole brief: no light tool

At i1 the caster measured **2,209 px differing from the empty stage** — he renders essentially
black. The crypt is dim, and **the `create_particles` family cannot create a light**; nothing on this
wire illuminates geometry. Arm H's own stated strongest technique — *"the bolt carries a light … the
floor is lit **by** the event … a particle system alone cannot do this"* — is unreachable here.

Named as a ceiling (L-G), then answered with the only lever the wire has: **the flash became a
backlight.** 60 → 220 particles in a 0.42 m shell seated on the hand, damped so every particle stays
within 0.73 m of the socket. The figure is not lit; it is **silhouetted inside the bloom** —
verified in frame, arm raised, readable.

i2 → i3 then fixed what that cost: 220 additive sprites at α1.0 **sum past white**, and the cyan —
the one thing separating this element from the crypt's warm light — was lost exactly where the effect
was brightest. Peak α dropped 1.00 → 0.85 with a cyan-biased ramp and `scale_max` 0.52 → 0.44 at a
higher count: granular, and the sum stays in hue.

The same iteration retightened the impact, and the cause there is structural rather than cosmetic:
**the alpha ramp delays APPEARANCE but never MOTION**, so whatever a delayed burst does during its
invisible 0.585 s is what the judge first sees. i2's burst popped in already expanded (rest radii
0.22–1.68 m) and read as a loose cloud. The fix is kinematic — damping 9 → 14, v 2.0–5.5 → 1.6–4.2,
rest radii 0.09–0.63 m — so the beat arrives as a core. The ground ring was pushed from a 1.15–2.4 m
annulus to 2.1–3.0 m so it clears the core and reads as its own floor beat.

### §1.6 ★ Wire hazard found (and it silently corrupted an iteration)

**`create_scene` refuses when its target is the currently-open scene** — *"Use live editor changes
plus save_scene, or close the scene before offline edits"* — and `save_scene` has **no target
argument**, saving whatever is current. i2's first firing hit both:

1. `create_scene` failed (1 of 24) and the run continued under `--continue`;
2. `open_scene` re-opened i1's **stale in-memory scene**;
3. the five `create_particles` calls appended to it and were **auto-renamed**
   (`@GPUParticles3D@19770` …) because Flash/Bolt/Trail/Impact/Ring were taken;
4. every subsequent `node_path`-addressed tuning call therefore **silently retargeted i1's nodes**.

Result: a 10-system scene, half of it untuned, and **every individual call reported OK**. It was
caught by the capture rig's dressing log, which prints each particle node's name and amount.

Two lessons, both general: **halt-on-error is the correct default for an authoring plan** (`--continue`
turned one refusal into a corrupted iteration), and **a wire that addresses by name needs a fresh
namespace per iteration** — every iteration since targets its own `.tscn`. A related first-contact
hazard: the very first smoke plan's `save_scene` wrote to `res://scenes/tcp_l2_pro_room.tscn`, a
**tracked** file left open from an earlier lap. Verified byte-identical no-op (`git diff` empty), so
no damage — but the wire will write to a tracked file it was never pointed at.

### §1.9 Ceilings named (L-G — a ceiling is a PASS)

1. **No light.** The particle family cannot create or drive a light source. Arm H's strongest named
   technique is structurally unavailable. Answered with backlight-by-additive-bloom; the caster is
   silhouetted, never lit.
2. **No timeline.** No delay, no sequencer, no per-system phase offset. Substituted by
   shared-lifetime + alpha-ramp windows — which delays **appearance but not motion**, so a delayed
   beat's kinematics must be pre-spent.
3. **No moving emitter / no `local_coords`.** Travel is carried by particle kinematics instead.
4. **Node timing is create-time only.** `amount` / `lifetime` / `one_shot` / `explosiveness` are set
   by `create_particles` and by nothing else, so any iteration that moves a count is a **full
   re-author**. Corollary: **`apply_particle_preset` overwrites all four**, so a preset's look cannot
   be composed with a chosen cycle — and the two burst presets (`explosion`, `sparks`) force
   `one_shot = true`, which makes them **invisible in any settled looping capture**. Six of eight
   presets are loopable; two are not reachable by this arm at all.
5. **`draw_pass_1` is never set by the wire** (verified at source and by readback) — a
   wire-authored particle system renders *nothing* until the stage supplies a mesh. PC-EXIT §4.3
   anticipated this and made it symmetric.

== the mobile aim bug (NOT fixed here, per dispatch) ==
Confirmed present. Noted for T4i, and one observation the exporter fix should account for:
keeper.gd's `_unhandled_input` is probably NOT the live path. `touch_controls.gd::_input`
calls `get_viewport().set_input_as_handled()` on EVERY InputEventScreenTouch — the CAST
button branch included — so `_unhandled_input` should never see that touch and
`vfx_cursor_override` should stay null. Aim then falls through to
`get_global_mouse_position()`, which on a web touch device is wherever the browser last
reported a (compatibility-emulated) mouse — i.e. the CAST button. Same symptom, different
seam: suppressing the override alone may not fix it if the mouse position is the real source.
Worth one probe before the fix is written.

Can the overlay pass a "this touch was the CAST button" signal cheaply? YES, and it already
computes it. `touch_controls.gd::_touch_down` hits
    if pos.distance_to(_button_center(button)) <= button.radius * 1.15:
exactly when a touch lands on CAST/JUMP/VFX. One member var on the autoload set there
(e.g. `var last_touch_was_button := true/false`, or an `aim_hint` the overlay owns) is a
one-line overlay change with no new nodes and no per-frame cost. The consumer side is
keeper.gd, which is exporter-owned, so nothing was changed on either side in this build.

== caveats ==
Unchanged from web8: iOS texture memory ~45 MB first download, the six big parallax/tile
  textures import as lossy WebP q0.9, and parallax/tiles/tile_0_0.png is 4096x4096 (at the
  GLES3 max-texture-size floor; devices reporting exactly 4096 are fine).
The two new kits add 117 PNGs / 665810 B of source art. Largest frame is 512x512, so
  none of it crosses the 2048 px lossy threshold — it all imports lossless. No new large
  texture in this build; the +884592 B on the pck is those two kits.
Single-threaded build (no SharedArrayBuffer), so no COOP/COEP headers are needed on Vercel.

== harness note for the next deploy ==
Firing `cast` from the keyboard needs `keyboard.down('KeyE')` held across a screenshot,
not `keyboard.press()`; and in headless swiftshader a `page.screenshot()` costs the better
part of a second, so the burst is caught by taking frames back-to-back with NO sleeps
between them, fired four times, then picking by pixel-diff against the pre-cast baseline.

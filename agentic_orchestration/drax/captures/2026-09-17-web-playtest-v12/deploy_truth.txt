== THE GREY — why "NONE" is a measurement and not a shrug ==
══════════════════════════════════════════════════════════════════════════════════════
Script: grey_measure.py in this directory. It corrects the web11 instrument TWICE, and
both corrections were forced by the instrument returning cleanly while answering a
different question than the one asked — the shape CLAUDE.md's commit-discipline block
keeps recording.

CORRECTION 1 — THE REFERENCE FRAME. My first pass differenced the cast frames against
the pre-cast frame, as web11 did. Between those two frames the Keeper had taken his
60 ms facing tap and the camera had panned after him, so the mask was mostly camera
drift spread across the whole width. It produced numbers. They meant nothing. The fix is
to difference against the ADJACENT frame of the SAME cast: during a cast keeper.gd
freezes velocity, so the camera is static. Control, two adjacent non-VFX frames of the
same cast: 465 and 994 changed pixels, against 35902 for the impact frame. That gap is
what says the mask is VFX and not drift.

CORRECTION 2 — WHAT "GREY" MEANS, and this one nearly filed a false defect report.
web11's criterion was saturation < 28 AND max channel > 110. Run unmodified on this
kit it reads 11-13 % "grey" on all three casts, which looks exactly like web11's defect
coming back. It is not. fire_bolt_e1_B HAS A WHITE-HOT CORE BY DESIGN, and near-white is
desaturated. The criterion cannot tell a white-hot core from an unshaded index map; it
was written against a kit that had no white core, and it was carried forward to one that
does. Split the desaturated pixels by MAX CHANNEL and the two separate cleanly:

                                  white-hot core   UNSHADED-GREY     warm
                                    (max >= 235)    (110-235)
  CONTROL cast1 f2 vs f1 (no VFX)      0.00 %        0.86 %         80.4 %
  CONTROL cast2 f3 vs f2 (no VFX)      0.00 %        2.52 %         66.9 %
  cast1 impact fan                    12.90 %        0.21 %         86.1 %
  cast2 bolt aloft                    11.01 %        0.00 %         76.9 %
  cast3 bolt aloft                    11.33 %        1.03 %         70.1 %

Every unshaded-grey reading is AT OR BELOW the no-VFX control floor. There is no
unshaded-grey population in this kit that is distinguishable from background noise.
The whole desaturated mass is the flame core, and it is 98 % of it.

Cross-check against web11's own archived exhibits, same instrument, whole frame:
  tcast_13_cast2_f2.png (the defective peak)   mid-grey band 110-200: 1.16 %
  REBUILD_clean_cast_peak_NO_grey.png (clean)  mid-grey band 110-200: 0.73 %
web11's defect lived in the MID-GREY band. web12's desaturation lives at 235-256. They
are different populations, and the one that mattered is absent.

MECHANISM AGREES WITH PIXELS, which is the part that makes this a finding rather than a
hopeful reading. web11's grey was CAUSED by two dangling shader references, and a
dangling shader announces itself: "invalid UID … using text path instead" plus "Cannot
load shader", six lines per run in the console. web12's production console has zero of
them, the build's dangling-res:// fence passed, and the import/export logs are clean.
Absent cause, absent symptom, and both measured separately.

== THE FENCE — a build-tooling fix this deploy required ==
══════════════════════════════════════════════════════════════════════════════════════
The first build FAILED and it was a FALSE POSITIVE. The overlay's license fence rejected
seven of the pack's own files:
    scenes/vfx_fire_bolt_e1_A_impact.tscn, scenes/vfx_fire_bolt_e1_B_impact.tscn,
    scripts/vfx_fire_bolt_e1_{A,B}_impact.gd, scripts/vfx_fire_bolt_e1_{A,B}_material.gd,
    scripts/keeper.gd (content)

The fence exists to stop library VFX packs being redistributed. Those ship as
vfx/<kit>/ and vfx_<kit>_(bolt|impact) for kits named EXACTLY frost/fire/lightning/
arcane/holy/poison. The pattern had no trailing boundary, so "vfx_fire_bolt" matched as
a PREFIX of the self-authored "vfx_fire_bolt_e1_A_impact". v44 is the first pack to ship
a fire_bolt_* kit, so this fence had never met the case it gets wrong. web/README.md
already claims the matching is exact ("lets self-authored kits like lightning_blast
through") — the claim was right, the regex did not implement it.

FIX: add the exact-name boundary in both copies of the pattern —
  _overlay/apply_overlay.py   …_(bolt|impact)(?![A-Za-z0-9_])
  build_playtest.sh (pck grep) …_(bolt|impact)[^A-Za-z0-9_]   (BRE/ERE has no lookahead;
      pck paths always carry an extension, so the boundary character is always present)

⚑ THE FIX WAS NOT ACCEPTED ON ITS ARGUMENT. Loosening a license fence to unblock my own
build is exactly the change that must not be taken on reasoning alone, so it was tested
against the real thing. Both library-bearing packs on disk — CS-pack-v8b and CS-pack-v14
(C-3), the two the fence's own comment cites as "hit 180 paths each" — were re-scanned
with the old pattern and the new one:
      CS-pack-v8b:  loose 180 hits, strict 180 hits, LOST 0  -> fence still fails
      CS-pack-v14:  loose 180 hits, strict 180 hits, LOST 0  -> fence still fails
Zero loss of catching power on the packs it was built to catch. Their real filename
shapes were enumerated rather than assumed: vfx_<kit>_{bolt,impact}.{tscn,gd}, 24 files,
nothing with a suffix after bolt/impact. My first regression attempt asserted a
"vfx_frost_bolt_material.gd" form and the new pattern missed it — I had INVENTED that
filename; it does not exist in either library pack. Enumerating the real shapes is what
settled it.

And the fence was then re-run against the LIVE production pck, downloaded independently
of the build: no match. Clean.

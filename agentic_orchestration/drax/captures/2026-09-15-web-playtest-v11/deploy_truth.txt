== THE DEFECT ==
══════════════════════════════════════════════════════════════════════════════════════

WHAT PRODUCTION DOES. Every cast of fire_burst_e0p_v2 prints, in the browser console:

  WARNING: 'res://scenes/vfx_fire_burst_e0p_v2_impact.tscn': In external resource #1,
    invalid UID: 'uid://g77d38ee0sf' - using text path instead:
    'res://vfx/fire_burst_e0p_v2/materials/vfx_material_mix_unlit.gdshader'.
  WARNING: ... external resource #29, invalid UID: 'uid://cqd6rx0tl7e5j' - using text
    path instead: 'res://vfx/fire_burst_e0p_v2/materials/vfx_material_add_unlit.gdshader'.
  ERROR: Cannot load shader: res://vfx/fire_burst_e0p_v2/materials/vfx_material_mix_unlit.gdshader
  ERROR: Cannot load shader: res://vfx/fire_burst_e0p_v2/materials/vfx_material_add_unlit.gdshader

Six lines per run here, 2 shaders x 3 casts. Full log in tcast_console.txt. Those two
paths are the PRE-RENAME names. They do not exist in v26 and they are not files in the
pck — only the references are. The materials that wanted them therefore load with a null
shader, and a null ShaderMaterial draws the raw piece texture. The piece textures are
greyscale INDEX maps; the shader is what maps them onto the fire palette. So the pieces
that lost their shader come out grey.

HOW MUCH OF THE BURST. Measured, not eyeballed: mask = pixels that changed against the
pre-cast frame, minus the CAST button; "grey" = saturation < 28 and max channel > 110.

  PRODUCTION (shipped pck)                CLEAN REBUILD (same source, same script)
  tcast_13_cast2_f2   grey 50.5 %         clean_07_cast1_f2   grey  0.1 %
  tcast_07_cast1_f2   grey 41.5 %         clean_11_cast2_f0   grey  0.8 %
  tcast_19_cast3_f2   grey 12.7 %         clean_13_cast2_f2   grey  0.0 %
  tcast_14/20 (residue phase) grey 0.1 %  clean_19_cast3_f2   grey  0.1 %

The residue phase is unaffected (the eroded tongues use shaders that survived); the PEAK
frame is where half the burst goes grey. Look at tcast_13_cast2_f2.png and
tcast_19_cast3_f2.png — the big pale metallic fans around the flame are not art, they are
unshaded pieces. REBUILD_clean_cast_peak_NO_grey.png is the same cast off the corrected
pck: the fans are gone and the burst is warm end to end.

⚑ WHY THIS PARTICULAR DEFECT IS WORSE THAN ITS SIZE. It disfigures exactly the thing
this deploy exists to show. A playtest of the live build would read the lap-3 burst as
wrong — and the kit is not wrong. A ruling against T4l/T4m taken off this URL would be a
ruling against my build error.

ROOT CAUSE, and it is mine, not the pack's. The mirror at web/cliffside keeps its .godot
import cache and its Godot-generated *.uid sidecars across runs by design (rsync excludes
them, so UIDs stay stable and the scenes do not re-import from scratch every build). v26
RENAMED two shaders. So on the first web11 build:
  1. rsync brought in the new names and deleted the old shader files;
  2. the prune step correctly removed the two now-orphaned *.uid sidecars — this is
     visible in that build's log and I read it as routine housekeeping;
  3. .godot/ still held the OLD uid -> OLD path map, and nothing had invalidated it;
  4. the Web export resolves scene ext-resources through that map, so it baked the
     pre-rename paths into the pck;
  5. nothing failed. Exit 0, sizes sane, license fence clean, local boot smoke test
     green. The only symptom lives in a runtime console a player never opens.
Step 2 and step 3 are the same event seen twice and the build treated them as unrelated:
pruning a sidecar IS the evidence that the uid map is stale, and it threw that evidence
away instead of acting on it.

This is the exact hazard web/README.md already writes down under "Gotchas" ("Deleting
them while keeping .godot/ gives mismatched UIDs ... move web/<route>/.godot aside and
rebuild"). It was documented, I had read it, and it still shipped — because the README
tells a human what to do when they NOTICE, and there was nothing to notice.

⚑ HOW I NEARLY MISSED IT TWICE, recorded because the near-miss is the finding. I first
tested the fix by serving the rebuilt tree on port 8767 — and the console still showed
the errors, which almost had me conclude the defect was in the v26 source. A PRE-EXISTING
python http.server from another session already held 8767; mine failed to bind and died,
and the old one answered with the OLD pck. The check ran, returned cleanly, and answered
a different question than the one I asked. What caught it was reading the size in the
harness's own response log: `200 ... 36688904` where the clean pck is 36689928. Same shape
as the instrument failures in CLAUDE.md's commit-discipline block. Standing habit from
here: a local-server verification must assert the bytes it was served, not just that it
got a 200. touch_cast_dummy.js and route_walk.js log every index.* response for this
reason; read that line before you read the console.

VERIFICATION THAT THE SOURCE IS INNOCENT. Three independent builds:
  a. shipped build (stale .godot + pruned sidecars) -> 2 dangling refs, 6 console errors
  b. same mirror, .godot moved aside, rebuilt      -> 0 dangling refs, 0 console errors
  c. clean-room build of pristine v26 into a brand-new route (web/cliffsideclean, since
     deleted), nothing inherited at all            -> 0 dangling refs
(b) and (c) agree on 36689928 B. v26 ships no uid:// strings and no .uid sidecars at all;
every shader path in every v26 .tres resolves to a file that exists. The pack is clean.

== BUILD-SCRIPT CHANGE (reincarnated-godot/web/build_playtest.sh) ==
Two changes, and the second is the one that matters.

1. SELF-HEAL. If the prune step removes any orphan sidecar, the script now drops
   $DEST/.godot before importing, with the reason printed. A pruned sidecar means the
   source renamed or removed a resource, which is precisely when the cached uid map is
   wrong. Regression-tested by reconstructing the failing state (orphan *.uid sidecars
   present alongside a populated .godot) and re-running: the clause fires, the log reads
   "orphan sidecars pruned -> dropping stale .godot import cache (uid map is now wrong)",
   and the resulting pck is byte-identical to the clean-room build.

2. DANGLING-RESOURCE FENCE, post-export, beside the license fence. Every res://*.gdshader
   path baked into index.pck must exist in the project; otherwise the build prints each
   offender and exits 3. Shaders are not remapped on export, so the path in the pck is the
   path on disk — no false positives. Dry-run against both pcks:
       shipped pck -> dangling: res://vfx/fire_burst_e0p_v2/materials/vfx_material_add_unlit.gdshader
                      dangling: res://vfx/fire_burst_e0p_v2/materials/vfx_material_mix_unlit.gdshader
       correct pck -> (nothing)
   The fence is the durable half. (1) fixes the cause I found; (2) fails the build for any
   dangling-resource cause I have not found yet, including one nobody has thought of. A
   silent bad pck is the thing to make impossible, not this particular silent bad pck.

⚑ Not fixed, noted: web/README.md's remedy tells you to move .godot aside INSIDE $DEST,
where the next rsync --delete removes the backup (it excludes the directory named .godot,
not .godot.anything-bak). Harmless — it is a cache — but it cost me the ability to replay
the original stale state exactly, so the regression test above reconstructs it instead of
replaying it. Worth moving the backup outside $DEST next time the README is touched.

== harness notes for the next deploy ==
Serve-and-verify: assert the BYTES, not the status. A local http.server that loses the
  port bind to an older session dies silently and the previous server answers; the harness
  logs "200 <type> <length> <url>" for every index.* fetch, and that length is the check.
  This nearly cost a correct v26 pack a false bug report.
Speeds come from the SCENE, not the script. cliffside.tscn overrides walk/run to 247/494.
  Anything that plans movement in seconds has to read the .tscn, not keeper.gd's defaults.
Plan routes against walkable.json MINUS the collide=true prop footprints, with a clearance
  penalty; a straight line from spawn to the clearing does not exist (the ravine), and the
  bridge corridor is narrow enough that a 45-degree hold walks off it.
Dead reckoning costs ~0.1 s per leg in keyboard latency. Plan, run, measure where you
  landed against a prop of known world position, subtract per leg, re-run.
Touch framing: the phone-landscape context letterboxes to 1388 of 1688 screenshot px.
  Calibrate screen<->world off two known props before trusting any position estimate.
Kit choice for aim questions still stands from web10: use a slow kit (frozen_orb). For
  the burst kits, fire the cast and take 6 back-to-back screenshots — f2 catches the peak
  and f3 catches the lap-3 residue, and nothing else catches either.

## (a) §2 composition-matched baseline — does it close RF-B, and does it open a new confound?

**Finding: CLOSES RF-B. Opens one new confound (C3) + one standardizer question (C1).** Verified first-hand: the OLD `sd_pool` was `between_kit_stdev` across 131 baseline cells that ALL shared the elite-heavy `open_arena` (3-elite+37-swarm, 1.5×) — `player_damage_total` pool_max = **19,575** (baselines JSON `pool_metric_variance_decomposition`), matching the report's ceiling claim exactly. The formations are homogeneous ~6,000-HP multisets, so the OLD contrast measured HP budget on 2 of 3 metrics. I confirmed the artifact directly in the W3 per-pair table: high-fit `d2-bowazon` shows `mobs_killed` d=0.0, `aoe_hits` d=0.0 (fighter clears both arms to 40/40), `player_damage_total` d=−2.13 (the 19,575-vs-6,000 budget gap). §2's per-pair identical-multiset baseline **removes exactly this**: both arms now carry the same mob multiset + HP, so the HP budget cancels in Δ alongside the fighter. RF-B is genuinely closed. Open-arena default placement is neutral across compositions (the arena's placement is composition-agnostic — it places whatever multiset it is given), so the baseline placement itself introduces no per-composition bias.

→ **C1 (WARN): the between-cell `sd_pool′` standardizer is now measuring across cells that no longer share a measurement context.** In the base sheet, all 32 pairs standardized against ONE common pool (the shared elite-heavy baseline set) — a coherent between-cell spread. Under §2, each pair has its OWN composition-matched baseline, so the 32 matched-baseline cells span 32 DIFFERENT compositions (swarm-40, magic-40, mixed, etc.) at DIFFERENT per-mob HP. The between-cell stdev of those 32 heterogeneous cells now conflates (i) genuine between-kit shape variation with (ii) between-COMPOSITION HP-scale variation — the very quantity §2 removed from the numerator is re-injected into the denominator's spread. This does not invalidate the gate (a fixed pre-results denominator introduces no circularity, per my W3 check dim-(b)), but it means `d = Δ / sd_pool′` is standardized by a spread that is partly composition-scale noise, which can DEFLATE effect sizes heterogeneously (a swarm-40 pair's Δ divided by a pool sd inflated by magic-40 cells). **Pin needed:** state explicitly whether `sd_pool′` is (a) the between-cell stdev of the 32 heterogeneous matched-baseline cells as written, accepted as a conservative (larger) denominator, OR (b) a per-metric pooled *within-composition* spread. If (a) — which is what §3 says — pin the one-line acknowledgment that X=0.5 is now measured against a composition-heterogeneous spread and is therefore *conservative* (harder to clear), consistent with the failure-safe posture. Verified at: freeze (I re-read §3 for the acknowledgment). This is the pin most load-bearing to interpreting a W3′ PASS/FAIL magnitude.

## (b) §3 sd_pool′ recomputation — fully mechanical? stamped BEFORE encounter scoring — verifiable how?

**Finding: MECHANICAL, one verifiability pin (C2).** The recomputation is a pure function of the 32 matched-baseline cells' 4-seed means — no discretionary step exists between data and stamp (it is the same `between_kit_stdev` computation the base pool used, applied to the new cell set). The X=0.5 standardized rule carries verbatim; only the standardizer's numbers move, which is correct — the old sd was a property of the retired elite-heavy set. **However**, §3 asserts the stamp lands "BEFORE any encounter fight is scored" but does not pin HOW that ordering is *verifiable* post-hoc. In a zero-discretion mechanical execution, the executor runs 256 fights in one process; nothing structurally prevents `sd_pool′` from being computed after encounter data exists in memory, then reported as "pre-gate."

→ **C2 (WARN): pin the ordering as an auditable artifact, not just a sequence claim.** The base sheet's analogous protection was the HEAD-stamp-at-open invariant (a checkable hash). §3 needs the equivalent: require that the 32 baseline fights + `sd_pool′` stamp be **written to the output JSON as a sealed sub-object BEFORE the encounter-fight loop begins** (e.g., a `sd_pool_prime_stamp` block with the 32 baseline cell-means and the derived sds, emitted and flushed prior to any encounter record), so the conductor's DRIFT-CRITIC pass can confirm the standardizer was fixed independent of encounter outcomes. Without this the "stamped pre-gate" claim is an assertion, not a verifiable invariant. §7's execution order lists this correctly ("sd_pool′ stamp → 256 fights") — C2 asks only that the *artifact* make the order checkable. Verified at: freeze (I re-read §3/§7 for the sealed-stamp requirement).

## (c) §4 metric-degeneracy rule — genuinely pre-pinned, or disguised leg-dropping?

**Finding: GENUINELY PRE-PINNED and NOT leg-dropping — with one decidability sharpening (C3).** This is the concern I stress-tested hardest, because a post-hoc metric-exclusion rule is exactly how a motivated analyst launders a FAIL into a PASS. The rule survives the stress test on three grounds: (1) it is **declared before data** with a fixed numeric criterion (`sd_pool′=0` OR ≥90% of matched-baseline cells at the hard structural bound), not a post-hoc judgment; (2) the ≥90% criterion is evaluated on the **BASELINE cells only** — computed at the same pre-gate stamp as §3, BEFORE encounter scoring — so an analyst cannot see encounter outcomes and then choose to drop an inconvenient metric; the degeneracy determination is causally upstream of the verdict; (3) the renormalization is **fully specified and monotone toward HALT** (3→≥2-of-3, 2→2-of-2, 1→sign-alone+LOW-POWER flag, 0→red-flag HALT) — critically, dropping metrics makes the gate HARDER to pass (2-of-2 must agree; 1-metric flags LOW-POWER; 0 halts honorably), never easier. A leg-dropping laundering scheme requires the drop to *help* the passing case; here every drop tightens or halts. That is the correct anti-gaming shape. **My empirical check confirms this rule is load-bearing, not decorative:** in the OLD pool only 14/131 (10.7%) cells cleared 40 mobs, but under §2 the baseline is the SAME weak ~6,000-HP multiset as the encounter — so the fighter that clears the formation to 40/40 will very likely ALSO clear the open-arena baseline to 40/40. mobs_killed (and aoe_hits, ceiling-coupled) will saturate in BOTH arms for a large fraction of pairs. §4 is the mechanism that stops that saturation from injecting spurious d=0.0's into the composite. Without §4 the W3′ gate would likely have measured `player_damage_total` alone by accident; §4 makes that explicit and honest.

→ **C3 (WARN): the ≥90%-at-bound criterion is decidable, but pin the tie-and-timing edges so no judgment survives.** Three sharpenings: (i) **which cells** — confirm the ≥90% is computed over all 32 matched-baseline cells' 4-seed *means* (a cell counts as "at bound" iff its 4-seed mean = 40), NOT over 128 individual fights, and NOT over encounter cells; §4 says "matched-baseline cells" but does not pin mean-vs-fight granularity. (ii) **exact threshold** — "≥90% of 32" = ≥28.8 → **≥29 cells**; pin the integer so 28-vs-29 is not an executor call. (iii) **the renormalization must be a pure function of the pre-gate degeneracy vector** — pin that the informative-metric count is frozen at the §3/§4 stamp and CANNOT change after encounter data arrives (e.g., a metric that looked informative on baselines but goes degenerate on encounters stays IN the composite — the determination is baseline-only, one-shot). This closes the only residual: an analyst re-running the degeneracy test post-encounter to reach a convenient renormalization. Verified at: freeze (I re-read §4 for the three pins). NOTE: the rule is *already* non-leg-dropping; C3 removes the last discretionary micro-edges, it does not change the rule's power.

→ **C4 (INFO):** a v2-fit-scoring artifact surfaced, not a W3′ concern: hole cells score fit=0.15 while the worst BUILDABLE cells score fit=0.10 — i.e., "no geometry dealt" (hole) scored *higher* than "geometry present but terrible fit."

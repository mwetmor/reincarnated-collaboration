## BLOCK-1 — `tokens_output` under-reported by 62 % on every U-11 row

### What I found

`claude_usage.aggregate_session` dedupes usage lines by `message.id` and keeps the **first**
occurrence. The module docstring states the premise that justifies this:

> *"Claude Code writes ONE transcript line per assistant content block, and every line of a
> multi-block message repeats the SAME `usage` object."*

**That premise is false, and it is false in 22,907 of 49,590 messages (46 %).** The three INPUT
axes do repeat identically. `output_tokens` does **not** — it is written progressively: the
non-terminal content-block lines carry a placeholder, and the message's complete output count
appears only on the terminal line.

Raw evidence, one message, verbatim from
`…/agent-a0587703762a450b9.jsonl`, `msg_011Ce1sPSdh5ntakPw97nP9F`:

```
out=1      stop_reason=None       content=['text']      "I'll start by reading the governing context a…"
out=1      stop_reason=None       content=['tool_use']
out=1      stop_reason=None       content=['tool_use']
out=401    stop_reason=tool_use   content=['tool_use']
```

Keeping the first line records **1** where the message cost **401**.

### The measurement (re-derived by this gate over all 27 rows' `derived_from`)

| axis | first-line (SHIPPED) | last-line | last `stop_reason`-bearing line | per-axis max | all agree? |
|---|---|---|---|---|---|
| `input_tokens` | 359,469 | 359,469 | 359,469 | 359,469 | ✓ |
| `cache_creation_input_tokens` | 204,120,185 | 204,120,185 | 204,120,185 | 204,120,185 | ✓ |
| `cache_read_input_tokens` | 8,238,067,996 | 8,238,067,996 | 8,238,067,996 | 8,238,067,996 | ✓ |
| **`output_tokens`** | **19,327,247** | **50,878,369** | **50,878,369** | **50,878,369** | ✓ (and ≠ shipped) |

**Three independent selectors — positional-last, semantic (`stop_reason` non-null), and
per-axis maximum — agree exactly on all four axes.** The result is over-determined, which is a
stronger finding than any one selector alone. Supporting property: `output_tokens` is
**non-decreasing across lines in 22,907 of 22,907 varying messages — zero counter-examples.**

### What is NOT affected — stated so the discharge is not over-scoped

- **`tokens_input` = 8,442,547,650 is CORRECT** and byte-exact under every selector.
- **cache-hit 97.578 % is CORRECT.** `tokens_cached_input` and `tokens_cache_write` are correct.
- **T3, the run's empirical criterion, SURVIVES.** The Claude cache-hit% renders beside Codex's
  from rows, and that number is true. **BLOCK-1 does not unseat T3.**
- Call count 49,590, repeated-lines 42,595 (46.2 %), and every row's `row_id`, `ts`, identity
  and `derived_from` re-derive **exactly**. Row-vs-substrate drift across all 27: **0**.

### Rationale

Discipline #74 (THE LAW): the board is a VIEW; a cell must be true to the substrate. Review
Principle #1: the arithmetic was asserted from a stated premise about the substrate rather than
measured against it — the one place in this build where math-before-code was not honoured, and
it is the place that broke. The premise was *checkable in one pass* and would have failed.

### Discharge conditions

      recommend the **semantic** selector (the line whose `message.stop_reason` is non-null,
      falling back to last-seen for the 1,534 messages that carry none) over the positional
      one, because a positional rule is silent if line order ever changes. All three selectors
      currently agree, so the choice is safe today and the semantic one stays safe.
- [ ] **star-lord:** correct the module docstring's premise. It currently asserts as fact
      something the substrate contradicts; leaving it is how the next reader re-introduces this.
- [ ] **star-lord:** emit `corrects:` correction rows for all 27 rows (the schema's only

      **⚠ This is blocked on BLOCK-2 — see below. The correction path does not currently reach

- [ ] **star-lord:** add the missing falsifier — a fixture in which a message's lines carry

## BLOCK-2 — the board is CORRECTION-BLIND: the tape's only amendment path cannot reach the render

### What I found

Discharging BLOCK-1 requires correction rows. I checked whether a correction actually changes
what the board says. **It does not.**

`bin/flight_report.unit_event` returns the **first** row of a given event kind in the unit's
ts-sorted rows:

```python
def unit_event(unit, event):
    for r in unit["rows"]:
        if r["event"] == event:
            return r
    return None
```

Proved empirically, not inferred — synthetic original CLOSE (`tokens_output=10`) plus a legal
correction (`tokens_output=999`, `corrects` set), run through the real `schema.fold` and the
real `unit_event`:

| correction's `ts` | rendered `tokens_output` | correction honoured? |
|---|---|---|
| same as original | **10** | **no** |
| later than original | **10** | **no** |

`schema.correction_errors` returns `[]` for both — the correction is **valid, accepted,
on-tape, and invisible.**

All 7 corrections currently on the tape amend `backfill` or `derived_from` only, so no
value-bearing correction has ever been rendered. The defect is latent and U-11's discharge is
the first thing that would hit it.

### Rationale

Discipline #74, one-data-path: the view must derive from the rows — *all* of them, under the
supersession rule the schema declares. MIGRATION.md § "Re-running" states corrections are *"the
only amendment path"*; SCHEMA.md § 3 states corrections *"SUPERSEDE"*. **Both are currently
prose with no parse-time consequence at the render** — the identical defect shape G-2b named
for `cost_usd` ("reported, never computed" was prose with no parse-time consequence).
Discipline #73: the state can change and the record will not follow it.

This is **pre-existing U-1 render-layer, not caused by U-11.** I charge it to this gate anyway
under Review Principle #3 (cross-seam impact): it is the discharge path for BLOCK-1, the two are
coupled, and ruling them separately would leave BLOCK-1 undischargeable.

### Discharge conditions

- [ ] **star-lord** (`flight/` seam): make the fold correction-aware — a row whose `row_id` is
      named by any `corrects` edge is **superseded** and must not be returned by `unit_event`
      nor summed by the scorecard/workstream aggregations (which iterate `closes` and would
      otherwise **double-count** the correction against its original).
- [ ] **star-lord:** derived test — an original plus its correction must render the
      **correction's** value, under both same-ts and later-ts orderings, and the pair must
      contribute **once**, not twice, to every summed cell.
- [ ] **ESCALATE — Matt / conductor:** confirm supersession is *fold-level law* (it changes
      every reader, drax's Tier-2 board included) rather than a `flight_report` local fix.
      Recommend fold-level, in `schema.fold`, so one home owns it — the WARN-2 lesson from
      G-2b, where two copies of one predicate diverged within the hour.

## Rulings

### R-G-U11-1 — F-1 (`tokens_input` = sum of anthropic's three input components): **RATIFIED**

The conductor's lean is upheld and star-lord's reasoning is adopted as given. The schema's
`tokens_input` axis means **total input presented, cached portion included**. Two proofs, both
independent of the emitter: Codex reports `cached_input_tokens: 750336` as a **subset** of
`input_tokens: 845782` on one turn; and every cache cell on the board is
`tokens_cached_input / tokens_input`, which is a **rate** only if the denominator is the whole.
Anthropic reports that same whole as three disjoint components. Storing their exact sum puts the
Claude lane on the schema's axis. The alternative renders cache-hit at several thousand percent —
a number wrong in precisely the way the recorder exists to prevent.

The sum is **exact, not an estimate**: every addend is a vendor-reported integer, nothing is
scaled, and fresh input stays recoverable as
`tokens_input − tokens_cached_input − tokens_cache_write` (= 359,469 for this population).
Verified by re-derivation: 8,442,547,650, byte-exact.

**On the SCHEMA.md clause — YES, REQUIRED. See WARN-1.** The ratification is not self-executing:
SCHEMA.md currently instructs the opposite.

### R-G-U11-2 — rev-1.2 provenance trigger: **NOT TRIGGERED.** The trigger stays armed.

The conductor's lean is upheld, and I sharpen the trigger so the next gate does not have to
re-litigate it.

G-2c deferred the provenance axis (instrumented vs authored) to *"the first instrumented
emitter."* U-11 is **not** one. It opens a finished transcript after the fact and assembles a row
from it; it witnesses nothing. Every row it writes is retrospective and correctly declares
`backfill: true` (27/27) — which is G-2c-R1 working exactly as ruled, not a gap awaiting v1.2.
The row's `event: CLOSE` with no START is the structural tell: **the emitter never saw a start,
because it was not there.**

**Trigger, restated for the next gate:** the provenance axis becomes live when an emitter writes
a row *from inside the harness whose event it records, at the time it records it* — i.e. when a
row could truthfully carry `backfill: false` as a positive claim of instrumented capture rather
than as an absence. Until such an emitter exists, `backfill`'s absence continues to assert
nothing (G-2c-R1, honest-null, the `LANE_REPORTS_COST` precedent).

**Note for the record:** U-11 makes the trigger *nearer*, not satisfied. A live in-harness
emitter is the natural sequel to this build, and it will arrive carrying this question.

### R-G-U11-3 — F-6 (synthetic-probe zero rows): **MEASURED ZEROS. CLEAN. No finding.**

Four rows carry `model_echo: "<synthetic>"` with all-zero token fields. I read the source files
named in their `derived_from` directly rather than reasoning about the code. The transcripts
contain, verbatim:

```json
{"input_tokens": 0, "output_tokens": 0, "cache_creation_input_tokens": 0,
 "cache_read_input_tokens": 0, … "service_tier": null, "speed": null}
```

**Explicit integer zeros, present in the substrate.** These are Claude Code's local synthetic
responses — real sessions in which no billable API call occurred. A measured zero is the correct
record, and this is the honest-null law's mirror clause, not a breach of it.

The mechanism behind it is also sound, which is the part worth banking: `iter_usage` **skips**
any line whose `usage.input_tokens` is `None`, so a genuinely null-usage line is never
zero-filled — it is dropped, not counted. I probed the whole population for the residual hazard
(a *partial* null, e.g. `output_tokens: null` coerced to 0 by `or 0` inside the sum):
**0 occurrences across all 27 sessions.** The hazard exists in the code but is not live on this
substrate; recorded as INFO-4 rather than acted on.

## Verdict

**ENDORSE-WITH-CONCERNS.** The extension-not-rewrite claim SURVIVES scrutiny — but only once rocket's soldering finding is folded into the headline. The spec composes with the existing fight engine rather than forking it, the COUNT≠CONTRIBUTION boundary is crossed cleanly (not smeared), and the four ENDORSE criteria are structurally feasible. The concerns are about SCOPE HONESTY and two structural pre-conditions Matt must weigh in the architecture decision, not about soundness of the cross itself.

## What I found

**Focus 1 — composes, does not fork (VERIFIED, holds).** I verified the single load-bearing structural fact directly in source: `_apply_skill_damage(attacker, targets_hit, ...)` (`spatial_engine.py:1326`) is genuinely target-agnostic — it takes a generic `SpatialEntity` attacker and a target list, decrements `target.hp`, and sets `is_alive=False` on death, with ZERO "is-this-the-player / is-this-a-mob" branching. gamora's claim that the damage path is allegiance-agnostic by construction is structurally honest, not aspirational. I confirmed the two hard-wired "mob" sites gamora names are the ONLY two: the `player`-hardcoded navigation target (`:954`, `target_x, target_y = player.x, player.y`) and the binary `all_entities = [self.player] + self.mobs` world (`:1662`). Generalizing exactly those two to allegiance-filtered sets is the crux, and the spec's extension-vs-fork line (§7.3) draws the boundary precisely where the code does. The minimal-path table (§7.5) names the fork explicitly as what is NOT being proposed, with a clean escalation disposition ("roadmap decision, not a wave"). This is an extension argument grounded in the substrate (Discipline #11), not a smear of bespoke logic through the loop.

**Focus 2 — the COUNT≠CONTRIBUTION boundary is crossed CLEANLY (holds).** gamora's two #12 semantic-shift declarations (§8) are the right two, and they are framed not buried. The critical one: the cancelled selector (`proxy_contribution_pct = proxy_damage_unit_seconds / (T + proxy_damage_unit_seconds)`, owner-DPS cancels) and the NEW realized-fight measure (`target.hp -= proxy_damage`, owner-DPS does NOT cancel) are kept as two distinct instruments measuring two distinct questions (classify-at-6b vs kill-the-boss). The spec is explicit that the realized path is ADDITIVE alongside the selector, NOT an upgrade of it — and names the §6 circularity hazard that conflation would re-introduce (the set inflating its own membership). This is the correct discipline. The contamination risk is named and structurally avoided, not merely asserted away. I checked the baseline note (`proxy-contribution-measure-and-set6-calibration-2026-06-17.md` §1.3): the cancellation is real and the "owner-DPS stops cancelling in a realized fight" pivot (spec §3) is the honest consequence, not a sleight of hand.

**Focus 3 — rocket's soldering finding MATERIALLY revises the scope headline (the load-bearing concern).** I verified rocket's central claim: zero export JSONs under `exports/` carry a `"proxies"` key (`grep -rl '"proxies"' exports/` → 0), and the sim reads `class_dict.get("proxies", [])` at `:2399` with an empty-list default. rocket is factually correct: the gen→sim proxy seam was specified at both ends and never soldered in the middle. The two seams speak different proxy vocabularies (gen: `proxy_power_per`/`proxy_count`/`proxy_geometry`; sim: `damage_multiplier`/`base_hp`/`range_m`/`targeting_behavior`) with no translator, and `_DEFERRED_PROXY_BINS` (`bc_target_composer.py:97,318`) defers every proxy bin before composition so the dict is never written. **This means gamora's "gen emits more fields into an existing dict" (§7.1) is optimistic — the dict does not exist.** rocket's correction is correct in kind: it is still an EXTENSION (no fork, rides the mob `hp_factor` / `_ENG_BIN_RANGE` / `proxy_offense_inheritance_s` patterns), but the generation column is a first-class ~1.5-wave workstream (G1 vocabulary-bridge + G2 stat-surfaces coupled to sim Waves 1-2; G3 Beast-Taming separable), not a secondary touch. gamora's "2-3 waves" headline holds ONLY if the generation half is counted explicitly rather than folded invisibly into "Wave 3 calibration." Folded, it undercounts.

**Focus 4 — buildable to the four design-fit criteria (structurally feasible).** Each criterion maps to a verifiable structural property: (1) solo byte-identical is guaranteed by empty-`proxy_decls` degeneration at `:2399` + the existing flag-gating precedent (Wave A2); (2) proxy boss-kill graded falls out of the `proxy_max_active` count-wall doing the boss-DPS-ceiling work for free; (3) `s < 1` is code-enforced at emit (`partition_roller.py:343`, verified via rocket's §5); (4) one shared survive-and-kill gate routes through the existing `boss_killed`/`mini_boss_killed` outcome resolution with no special-cased proxy gate. All four are structurally feasible. Whether they are the right DESIGN is gandalf's call, not mine — I am gating feasibility only.

## Structural concerns Matt must weigh (the architecture-decision inputs)

1. **The headline scope is materially larger than gamora's spec implies, once the generation column is counted honestly.** Not larger in KIND (still an extension, no fork) — larger in the sense that the gen→sim seam soldering (rocket's G1/G2) is a PREREQUISITE for gamora's Wave 2 EXISTING, not a parallel secondary touch. Matt should read the true total as: sim Waves 1-2 + generation G1/G2 (coupled, must land first or concurrently) + calibration Wave 3 + G3 (separable). The "2-3 waves" framing is defensible only with that decomposition explicit.

2. **Even the de-risk spike (T2.3) has a thin generation dependency the spec under-accounts.** gamora's spec frames T2.3 as a "throwaway spike" that resolves the load-bearing unknown (does the army kill the boss gradedly). But rocket correctly notes the spike needs SOME generation-emitted proxy stats (`base_hp`, a `damage_multiplier` mapped from `proxy_power_per`, a `range_m`) to run a fighting army at all. The spike is not zero-generation-cost. It can use hand-stubbed proxy stats (legitimate for a throwaway), but Matt should know the spike's "throwaway" framing carries a thin G1/G2 stub dependency — the spike does not de-risk the generation soldering itself.

3. **The whole workstream sits behind the Matt-reserved `_DEFERRED_PROXY_BINS` lift.** Both notes correctly mark this OUT of the current run. But it is worth surfacing as the architecture-decision gating fact: generation G1-G3 cannot START until the content-emission gate is lifted, and that lift is Matt's reserved call. The decision packet Matt is being handed is therefore "approve the SHAPE of the cross + authorize the spike," NOT "authorize the build" — which is exactly how both notes frame their HARD-STOP. The concern is only that the gen workstream's start is gated on a decision Matt has not yet made, so any wave-sequencing must treat the gate-lift as the true T0.

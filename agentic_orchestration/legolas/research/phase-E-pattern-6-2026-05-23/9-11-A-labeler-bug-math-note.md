## § 1. What the function does (verbatim, with line numbers)

The provisional description is generated by two functions in `phase_e1_pipeline.py`:

### `characterize_cluster` (lines 553–582)

```python
def characterize_cluster(rows, labels, cluster_id):
    indices = [i for i, l in enumerate(labels) if l == cluster_id]   # line 556
    ...
    names_lower = [rows[i][1].lower() if rows[i][1] else "" for i in indices]  # line 563

    # Weapon type detection
    type_counts = Counter()                                            # line 566
    for name in names_lower:                                          # line 567
        for token in WEAPON_TYPE_TOKENS:                             # line 568
            if token in name:                                         # line 569
                type_counts[token] += 1                              # line 570
    top_types = type_counts.most_common(3)                           # line 571
```

`indices` is the full membership set of the cluster — ALL rows (both `hdbscan_native` and `nearest_centroid`). `names_lower` therefore contains canonical names for every member of the cluster, not just the top-K representative rows.

### `propose_provisional_cluster_description` (lines 624–636)

```python
def propose_provisional_cluster_description(char):
    ...
    top_types = char.get("top_weapon_types", [])     # line 629
    ...
    type_str = "/".join([t[0] for t in top_types[:2]]) if top_types else "mixed"  # line 633

    return (f"PROVISIONAL: {lineage} {period} {type_str} weapons "   # line 635
            f"({register} register; {kind}; N={count})")              # line 636
```

`type_str` takes the top-2 tokens from `top_types` — which are the globally-counted tokens across all cluster members (line 571).

## § 3. Root cause classification

The bug has **two compounding root causes**:

### Root cause A — Wrong aggregation scope (PRIMARY)

`characterize_cluster` aggregates weapon-type token counts over **all cluster members** (line 556–570), including nearest_centroid-assigned rows (low-confidence, ~0.05 range). These low-confidence members contribute noise that can outvote or match the actual high-confidence representative pattern.

In Cluster 9, 59 "dagger" matches and 56 "wand" matches from low-tier named-template members overwhelm 5 "javelin" matches from the actual high-confidence reps.

In Cluster 0, the tie-breaking behavior of `Counter.most_common()` on a cluster with mostly unrecognized names (revolvers, kukris, wakizashi — none match the 30 tokens) allows 1-occurrence nearest_centroid members ("throwing axe", "staff sling") to dominate.

### Root cause B — Substring false-positive matching (SECONDARY)

The token match at line 569 uses `if token in name` — a bare substring check. This causes "lance" to match inside "Ambulance" and "Surveillance", and potentially other false positives. For Cluster 23, this is the PRIMARY error driver (all 5 "lance" matches are false-positives from ambulance/surveillance).

The structured-feature multi-hot in `build_structured_features` (lines 172–175) uses the same pattern (`if token in name_lower`) but there its effect is on the feature matrix, not the description generator. The description generator inherits this flaw independently.

### Root cause C — Token vocabulary coverage gap (TERTIARY)

The 30-token `WEAPON_TYPE_TOKENS` list does not cover many real weapon forms in the substrate: revolver, pistol (covered), kukri, wakizashi, tanto, javelin, SPH, MANPADS, UAV, APC, IFV, mine, grenade-launcher, flamethrower, etc. For clusters whose dominant forms are not in the 30-token list, the function emits whichever rare matches appear in the member pool. This compounds root cause A — if the real form is unrecognized, one stray match in a low-confidence member becomes the top token.

## § 4. Fix approach

### Recommendation: Approach A — rep-canonical-name-grounded

Derive the weapon-form description from regex word-boundary matches against the **top-K hdbscan_native representative rows' canonical_names** only (the `top_reps` list already computed in `write_clusters_subsample` via `get_top_representatives`).

The fix changes `propose_provisional_cluster_description` to accept the `top_reps` list as an additional argument and match weapon-type tokens against those names only — using word-boundary regex to eliminate substring false-positives.

**Why Approach A over Approach B (structural-only):**

- `top_reps` are the highest-confidence hdbscan_native rows — they are the most rep-faithful signal for cluster identity.
- gandalf's override evidence shows that for 30/47 clusters, the rep canonical_names DO contain recognizable weapon-form signals that could have produced a correct provisional description. Approach B would strip this signal entirely, requiring gandalf to do more inference work in Phase E-2.
- The 17/47 clusters where rep evidence is insufficient (contemporary military hardware, metadata residue, cross-form bundles) should fall back to "mixed" rather than emitting a false token-pair.

**Why NOT the current all-member approach:** demonstrated above — swamps rep signal with low-confidence member noise and introduces substring false-positives.

### Fix mechanics

1. Add `word_boundary=True` regex matching: replace `if token in name` with `re.search(r'\b' + re.escape(token) + r'\b', name)` to eliminate "lance" in "ambulance".
2. Pass `top_reps` to `propose_provisional_cluster_description`; match tokens against rep canonical_names only (3–5 reps, not 46–10,087 members).
3. If no token matches any rep name, emit `"mixed"` rather than picking stray full-member tokens.
4. To avoid regressions on correctly-labeled clusters (the 78 non-overridden), keep the same outer description format; only change the `type_str` derivation.

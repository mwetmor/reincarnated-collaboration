## 2. THE FOUR LOAD-BEARING RULINGS

### Ruling 1 — focus/combo cost_type drift (§2.3.3.1): **R-b (adapter post-hoc restamp). RULED.**

**The problem rocket correctly surfaced:** `_ROLE_COST_TYPE_PRIORITY["damage"]` ranks `rage > combo > focus`, so `starved` resolves rank-1 to `rage` not `focus`, and `generator-spender` resolves to `rage` not `combo`. A hunter (focus) or rogue (combo) damage kit would silently become rage — wrong power_tier (58→65), a hidden second variable. R-a (accept the drift) is correctly REJECTED: it perturbs the balance loop, which is exactly the cert-wave attribution error the whole program guards against.

**R-b vs R-c.** R-b restamps `ComposedKit.cost_type` + re-derives `resolve_power_tier(energy_type)` in the adapter AFTER `compose_kit` returns; the composer is untouched. R-c adds `energy_hint` to `resolve_cost_type`/`compose_kit`; cleaner semantically but a composer-signature change to a module SHARED with the Cycle-12 sampler family.

**I rule R-b.** Three reasons, in priority order:

1. **#13a is preserved either way, but R-b preserves the one-variable discipline harder.** I verified `resolve_cost_type` already takes `role` as an input — so energy_type as a population property is the same justification class as role (rocket's §10 claim, which I confirm: energy_type is a mechanical population property, NOT a substrate). Neither option violates #13a. But R-c changes the signature of a function shared with the Cycle-12 sampler — that is a second variable (a cross-consumer signature change) bundled into a behavior-preserving cut. R-b confines the entire change to the adapter, which is net-new code this stage creates anyway. The adapter is the correct seam for reconciling the orchestrator's already-chosen energy with the composer's internally-resolved cost_type, exactly as it is the correct seam for binding provisional substrate (§7.3). **Same architectural logic: the adapter is where the substrate-blind composition becomes the substrate-and-population-bound playable kit.**

2. **The restamp is sound because the mechanic SHAPES are cost-type-agnostic in the pool.** Rocket's §2.3.3.1 establishes that for focus/combo the geometry/range/cc of the sampled mechanics don't depend on the cost_type label — only the cost_type label and power_tier do. So restamping the label + power_tier after the fact does not invalidate the mechanic sampling that already ran. This is the load-bearing correctness argument and it holds: the cost_type-filtered mechanic sampling inside `compose_kit` ran on the econ_bin's resolved cost_type; the adapter corrects only the two scalar fields that diverge. **Confirm at implementation: verify empirically that no mechanic in the focus/combo damage pools is gated such that its presence/absence flips between the econ-resolved cost_type and the orchestrator's energy_type.** If any mechanic IS cost-type-gated in a way that changes the SET of sampled mechanics (not just their labels), R-b's "shapes are agnostic" premise breaks for that mechanic and the restamp would hide a kit-composition difference — escalate back to me if found. I expect it won't be (rocket's read is the pool is shape-agnostic on cost_type), but this is the one place R-b has a hidden assumption and the implementation must discharge it.

3. **R-c stays on the table as the Phase-5/diversification-era refactor.** When diversification lands and the orchestrator may emit energy choices the legacy maps never produced, the `energy_hint` param becomes the clean home for the constraint. Note in the implementation that R-b is the Stage-1 minimal-surface choice and R-c (`energy_hint`) is the registered successor when the composer is next opened for diversification — recognition→validate→commit: the cleaner signature commits when there's a second consumer that needs it, not now.

**Fold-in obligation:** the adapter restamp must carry a comment naming it as the focus/combo cost_type reconciliation, cross-referencing §2.3.3.1, and stating the "shapes are cost-type-agnostic" premise it rests on (so a future reader knows what to re-verify if the pool changes).

### Ruling 2 — `allocate_stats_from_coordinate` is a sixth adapter component (§4.3): **IN STAGE-1 SCOPE. Keys on (role, def_bin) NOT label. RULED.**

**Rocket is correct that the §7.4 contract implies this but didn't enumerate it.** I enumerated five components in §7.4; the cut breaks `allocate_stats(archetype)` (`stat_allocator.py:118`, which I verified IS label-keyed), and the contract's principle 1 ("no label consulted, ever") makes the label-keyed allocator unusable on the live path. **A coordinate-keyed allocator is therefore not optional — it is a structural consequence of the cut, the same way the PoolMechanic→Skill resolution layer is.** I accept it into Stage-1 scope as the sixth adapter component. This is not scope creep; it is completing the enumeration my §7.4 under-specified. Good catch by rocket — this is precisely what the math-FIRST gate exists to surface.

**How it keys — RULED:** `allocate_stats_from_coordinate(role, bc_target, rng)`, keyed on `(role, def_bin)` primarily (def_bin: tank/mitigator→VIT-primary, glass→offense-primary) refined by role (control→INT/WIS, damage→primary-offense-stat), per rocket's §4.3. **It must NOT key on the label, and it must NOT key on `dominant_element`** (stats are substrate-blind in the legacy allocator for elemental archetypes — the per-archetype distributions are role/defense-shaped, not element-shaped; binding element into stats would be a NEW coupling the legacy path didn't have, i.e. a second variable). The mapping table is derived from the existing `stat_allocator` per-archetype distributions tabulated against `(role, def_bin)` — behavior-preserving by construction.

**The one constraint I add:** rocket's §4.3 says "maps def_bin + role to the SAME stat distribution the legacy label produced for the corresponding archetype." That is the right target, but it has a collision risk: if two legacy archetypes share a `(role, def_bin)` pair but had DIFFERENT stat distributions (e.g. a focus-hunter and a rage-warrior both at `(damage, glass)` but with different DEX/STR splits), the `(role, def_bin)` key under-determines the distribution — the same under-determination shape as the focus/combo cost_type problem. **Resolution:** key on `(role, def_bin, energy_type)` if and only if the tabulation reveals such a collision (energy_type already in hand at the adapter, already a permitted population property per Ruling 1). If `(role, def_bin)` alone is collision-free across the 24 legacy archetypes, keep it two-dimensional for minimalism. **Fold-in obligation:** the implementation note must include the tabulation of the 24 legacy archetypes' stat distributions against `(role, def_bin[, energy_type])` and explicitly state whether a collision forced the third key dimension — so the behavior-preservation claim is auditable, not asserted.

### Ruling 3 — tier/chain "behavior-preserving" tolerance (§5.4): **TOLERANCE GRANTED. Acceptance = "valid tree the sim walks" + per-axis-equivalent topology, NOT template-identical. This is the crux; ruled explicitly. RULED.**

This is the one ruling only I can make and the one the dispatch flagged as the crux. I grant the tolerance, with a bounded definition of what "valid" means so it cannot become a loophole.

**Why the tolerance is correct and NOT a behavior-preservation violation:**

The b6 template's EXACT tier/chain tree (which skill is T1 vs T4, which skills chain to which) was a **per-template authored artifact**. The coordinate does not carry it — by design. The 8-tuple carries the kit's MECHANICAL POSITION (engagement, geometry, control-density, tempo, variance, defense, economy); it does not carry "skill #3 is the T4 capstone of chain B." That tree topology was a property of the TEMPLATE, which is exactly the thing we are deleting. **Demanding the coordinate reproduce a per-template tree it structurally cannot carry would be demanding the cut preserve the disease's artifacts — a contradiction.** The tier/chain tree is not a behavior the PLAYER experiences as kit identity; it is an internal organization the b6 builder used to assemble the kit. What the player feels — the kit's mechanical shape: what fires, at what range, with what control, at what tempo, at what magnitude — is the MECHANIC set, which §5.2 preserves 1:1 (geometry, range_m, energy_cost, cooldown, cc_effect, power_tier all straight from the PoolMechanic). **The mechanics are 1:1; the tree is coordinate-derived-valid. The player feels the mechanics, not the tree.**

This is the genre point made concrete. In D2, a Sorceress's skill TREE (which skill is a prerequisite of which) is a UI/progression-organization artifact; what makes the Frozen-Orb build the Frozen-Orb build is the MECHANICS (the orb's geometry, the cold damage, the tempo), not which tree-tier the synergy skills sit at. We retired set-dungeon rigidity (class = fixed template) for build-space-region identity (§3); the tier/chain tree IS a vestige of the set-dungeon's fixed-template organization. Carrying it forward 1:1 would re-import the very rigidity the cut exists to remove.

**The bounded definition (so "valid" can't drift into "anything"):** acceptance for tier/chain in Stage 1 is:

1. **Schema-valid:** every skill gets a tier ∈ {1,2,3,4} and a `chain_id` + chain_position + parent links that satisfy `skill_schema` and that the simulator's tree-walk traverses without error (no orphan parent refs, no cycles, no missing-tier gaps the walker assumes).
2. **Coordinate-consistent topology, not arbitrary:** the tier assignment must be DERIVED FROM the mechanics' own properties (rocket's §5.4: order by `skill_power_tier_base`/cd into tier bands — cheap/low-cd basics → T1, high-magnitude capstone → T4; chain_id by geometry-family clusters). It must NOT be a flat or random assignment. The topology is a deterministic function of the composed mechanics, so two identical mechanic sets produce identical trees (reproducibility) and the band structure reflects the actual magnitude/tempo gradient of the kit.
3. **`cross_chain_rule = "STRICT"` for all Stage-1 mono-element kits** (rocket's §4.4 default) — confirmed below in Ruling 4, this matches legacy non-hybrid behavior.

So the tolerance is precise: **MECHANICS 1:1 (no tolerance), TREE TOPOLOGY coordinate-derived-valid-and-deterministic (tolerance granted within the bounded definition above).** This is NOT "approximately preserving"; it is "preserving exactly the layer the coordinate carries (mechanics) and deterministically deriving the layer the coordinate doesn't carry (tree organization) from those same mechanics."

**The empirical backstop that makes the tolerance safe:** the A3 calibration gate (§9) simulates the 24 default-coordinate kits and measures their actual BC coordinate. If the coordinate-derived tier/chain topology caused the kit to PLAY differently enough to land >1 bin off-target on any axis, A3 catches it — because the AI rotation walks the tree, and a badly-derived tree would shift the kit's measured tempo/engagement. **So the tier/chain tolerance is not granted on faith; it is granted with A3 as the empirical proof that the derived tree preserves the kit's measured mechanical position.** This is recognition→validate→commit applied to the tolerance itself: I grant the tolerance now (recognition: the coordinate can't carry the tree, mechanics are what matter), A3 validates it (the derived tree keeps the kit at its target cell), and if A3 fails for tree-topology reasons the §2 bin-derivation OR the §5.4 tier-banding recalibrates before Stage-1 tags. **Fold-in obligation:** the implementation note must state that the §5.4 tier/chain derivation is subject to the A3 gate as its behavior-preservation backstop, and that an A3 failure attributable to tree topology recalibrates §5.4, not just §2.

**This is where I push hardest on one thing:** the tolerance is granted for tier/chain TOPOLOGY only. It does NOT extend to the mechanic SET, the mechanic shapes, the kit_size, or the cost/power calibration. If during implementation the §5.4 tier banding can't produce a schema-valid tree without DROPPING or ADDING a mechanic, that is not a tier/chain tolerance question — that is a kit-composition change, and it escalates to me as a behavior-preservation violation. The tolerance buys tree organization, nothing downstream of it.

### Ruling 4 — the remaining §11 items (mono-element / experimental bc_target / legacy-suffix table / infeasibility policy): **ALL CONFIRMED as rocket leans, with two conditions. RULED.**

- **§3 mono-element Stage-1 (`secondary_elements={}`, `is_hybrid=False`, `secondary_element=None`): CONFIRMED.** `compose_kit` is element-blind by construction, so the composer cannot produce a hybrid; the legacy hybrid-promotion came from `STAT_ELEMENT_POOLS` rolls in a SEPARATE pipeline surface not driven by `compose_kit` (rocket §3). Forcing hybrid re-introduction into Stage 1 would require wiring a second, element-aware path into the substrate-blind cut — a second variable, and worse, it would bind multi-element identity at generation, which is precisely the Phase-5/diversification concern. Mono-element is the correct behavior-preserving Stage-1 choice. **Condition:** the implementation note must REGISTER hybrid-promotion as a known Stage-1 behavioral DELTA (the one place Stage 1 is not bit-identical to legacy — legacy multi-element kits become mono-element), flag it as Phase-5/diversification scope, and the A3/round-trip smoke must be run on mono-element-coordinate fixtures so the delta is bounded and known, not silent. This is the second documented relaxation alongside tier/chain — and like tier/chain it is acceptable because the multi-element identity was a property of a separate pipeline surface the cut doesn't touch, not a property of the coordinate. **It must be NAMED in MIGRATION.md, not buried.**

- **§4.5 experimental kit `bc_target=None`: CONFIRMED.** The experimental slot is deliberately uncoordinated (grammar-direct, `archetype="experimental"` sentinel, already lock-compliant for skill gen, already not using `ARCHETYPE_TEMPLATES`). A measured-post-hoc coordinate would imply the experimental kit HAS a coordinate identity, which contradicts its purpose (it's the off-coordinate probe slot). `None` is correct and is the honest representation: experimental kits are the one place a kit legitimately has no bc_target identity. The nullable `bc_target` field (§4.1) exists precisely to carry this. Confirmed.

- **§6 legacy-suffix derivation table (role+bins → mage/caster/controller/physical suffixes) as coordinate→legacy-string OUTPUT: CONFIRMED.** This is acceptable because it is the INVERSE of the shim's behavior-target table, used as OUTPUT, never read back as INPUT (V-1..V-9 all re-pointed). The acceptance-check that makes it safe is already in the note (§6: "no generation code reads `PlayerClass.archetype_tag`/`classify_archetype` output as an input post-cutover"). The legacy-format string exists ONLY to keep the still-label-keyed Stage-1 simulator running (the decoupling buffer, §7.6); it dies in Stage 3. **Condition:** the suffix-derivation table must carry a `# INTERNAL-BRIDGE(dies Stage-3): coordinate→legacy-format OUTPUT; never read as input` comment at its definition, so no future reader mistakes the OUTPUT table for a re-introduced INPUT lookup. The whole danger of this table is that it LOOKS like the disease (it produces `{element}_{role}` strings); the comment + the grep guard (output-only, never an input read) are what distinguish it. With those, confirmed.

- **§7 infeasibility policy "log + re-draw class seed" (NOT degraded 5-skill kit): CONFIRMED, with one design point.** Routing `compose_kit`'s `None`/`DeferredEvaluation` to "log + re-draw a different class seed" rather than a degraded 5-skill fallback is correct AND is the philosophical core of the whole cut: **infeasibility becomes a principled composition-time outcome, not a silent degraded kit** (my §2.4-of-the-ruling acceptance: "the 1/29 is not tuned away; its code path ceases to exist"). The water_mage 1/29 dissolved precisely because the degraded-fallback path is removed. A re-draw preserves the season's class count without corruption. **The design point I add:** for Profile-A legacy coordinates, `None`/`Deferred` should NOT occur (the shim table proves they all compose clean) — so if a re-draw EVER fires in Stage 1, that is a SIGNAL, not routine. The log must be loud enough that a Stage-1 infeasibility surfaces as "a legacy coordinate that was supposed to compose clean did not" — an investigation trigger, not a swallowed event. **Fold-in obligation:** the infeasibility log must record the bc_target that failed + the role/range/energy/element that produced it, at a severity that surfaces in the season summary (not a buried debug line), so a Stage-1 infeasibility is impossible to miss. A re-draw that silently masks a real composition bug would re-create the water_mage 1/29's original sin (a degraded outcome nobody noticed) in a new form. Loud-fail is the discipline.
